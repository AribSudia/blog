عندك مشروع وتحتاج الذكاء الاصطناعي يساعدك بجدية — لا مجرد إجابة على سؤال.

في **CCM (Claude Code Methodology)** هناك أداتان مختلفتان جوهرياً لهذا:

- **`/arib-engine`** — يكتشف عمله بنفسه ويُنهيه بالدليل لا بأوامرك
- **`/arib-build`** — تعطيه هدفاً، يُفكّكه على فريق متخصص، يُسلّمك النتيجة

هما أخوان لا بديلان. السؤال: **متى تستخدم أيهما؟**

---

## الفرق الجوهري

### `/arib-engine` — المحرك المستقل

تخيّل مهندساً تعطيه **ملكية المشروع** لا قائمة مهام. يُحلّل، يكتشف المشاكل، يُصلحها، يتحقق، ويعيد الكرة — حتى يقول **الدليل** إن العمل انتهى.

```
discover → ship → verify → integrate → record → (هل انتهينا؟ → كرّر)
```

**السؤال "هل انتهينا؟" يُجيب عليه الدليل:**
- الـ backlog مُستنفَد
- ما تبقّى قرارات للمشغّل فقط
- الـ trunk أخضر

### `/arib-build` — مدير الفريق الهندسي

تعطيه هدفاً محدداً — يُفكّكه إلى مهام، يوزّعها على متخصصين **بالتوازي**، يجمع النتائج، ويُمرّرها بوابة الدمج.

```
decompose → dispatch (parallel) → integrate → reconcile → merge gate
```

المتخصصون لا ينتظرون بعضهم — **يعملون معاً** مثل فريق هندسي حقيقي.

---

## المقارنة المباشرة

| الخاصية | `/arib-engine` | `/arib-build` |
|---------|---------------|---------------|
| **نقطة البداية** | مشكلة مفتوحة | هدف محدّد |
| **يكتشف العمل؟** | ✅ adversarial find→refute→confirm | ❌ أنت تُحدّده |
| **الإيقاع** | مستمر حتى اختبار الإغلاق | جولة واحدة |
| **التوزيع** | دورة واحدة لكل جولة | متخصصون بالتوازي |
| **"هل انتهينا؟"** | الدليل يُقرّر | الهدف يُقرّر |
| **مع `/loop`** | ✅ الطريقة الطبيعية | ❌ غير مصمّم لها |
| **حجم الـ skill** | 300 سطر | 70 سطر — مُركّز |
| **المناسب لـ** | حملة مستمرة / مشكلة مفتوحة | تسليم هندسي محدّد |

---

## مثال عملي

**المشكلة:** تريد تحسين أمان المشروع.

**بـ `/arib-engine`:**
```bash
/loop /arib-engine harden the codebase
```
يُحلّل كل الأبعاد، يُحدّد الأولويات، يشحن PR بعد PR، يتوقف لما يُثبت إنه "خلّص فعلاً".

**بـ `/arib-build`:**
```bash
/arib-build "add input validation, rate limiting, and JWT hardening"
```
يوزّع على Security Engineer + Backend Architect + QA بالتوازي، يجمع، يُسلّم.

**الفرق:** الأول يكتشف **ماذا** يصلح. الثاني يعرف **ماذا** وينجزه أسرع.

---

## متى تختار أيهما؟

### استخدم `/arib-engine` حين:
- المشكلة مفتوحة — "صلّح ما يحتاج تصليح"
- تحتاج من يكتشف الأولويات بنفسه
- تريد حملة مستمرة بـ `/loop`
- لا تعرف بالضبط ما المطلوب

### استخدم `/arib-build` حين:
- الهدف محدّد بوضوح
- تريد تسليماً في جولة واحدة
- عندك مواصفات جاهزة للتنفيذ

### اجمع بينهما:
```
/loop /arib-engine discover    ← يكتشف الأهداف
          ↓
/arib-build <كل هدف>          ← يُنجز كل هدف بالتوازي
```
الـ engine يكتشف، البيلد يُنجز.

---

## التصميم خلف الاختيار

كلاهما جزء من **CCM v3.14.0 "Engineering Manager"** — لكن لأغراض مختلفة:

- `/arib-engine` صُمّم للمشكلات **المفتوحة** — لا تعرف نهايتها مسبقاً
- `/arib-build` صُمّم للتسليم **المحدّد** — تعرف النهاية وتريد أسرع طريق إليها

حجم الـ skill يعكس الفلسفة: الـ engine (300 سطر) يحمل آلية الاكتشاف والإغلاق. البيلد (70 سطر) مُركّز على **التوزيع والتجميع** فقط.
